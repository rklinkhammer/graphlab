# M4: QEMU and recorded consoles

M4 adds a Linux host QEMU backend, independently supervised C++23 serial/SSH/Docker console workers, bounded writer leases, durable output replay and browser terminals. [Preserved guest templates](../qemu-guests/README.md) qualify PowerPC/TCG and native ARM64/KVM. No Python implementation or guest support was introduced.

## Execution and ownership

Keep the M2 account separation and M3 capture prerequisites. Install `lab-terminal` beside `lab-agent` and `lab-capture` in a trusted root-owned directory. QEMU needs qemu-img, the architecture-specific QEMU binary, pinned machine support, matching firmware and a verified raw base disk. KVM admission requires `/dev/kvm` access and a native guest ISA; TCG is an explicit artifact-lock choice. Firmware, disk, optional kernel/initrd and SSH known-hosts blobs are digest-verified in `STATE/artifacts/<sha256 hex>`. SSH client credentials are separate private root-owned files at `STATE/credentials/<workload>.key`.

The executor journals owned descriptors before launch, creates per-run overlays and persistent TAPs, and launches QEMU paused with private Unix QMP/serial sockets. QMP is an agent/worker implementation detail, never a browser control endpoint. The worker attaches serial before release. Required captures arm on declared data edges before QMP continue. Process startup is distinct from guest readiness: the minimal guest emits `GRAPHLAB_READY`; third-party guest readiness is not inferred from a QEMU PID. Serial coverage is explicitly **from attachment**, with no first-byte guarantee.

The independent systemd worker renews no authority itself. A ten-second monotonic traffic lease expires into QMP stop; expired leases cannot be renewed into release. A worker failure kills its QEMU child. Agent restart adopts surviving workers under a higher generation and quiesces into reconciliation, without implicit guest release. Cleanup stops owned workers before deleting owned TAPs, while retaining overlays and recordings. Identity ambiguity is retained for recovery rather than deleting unrelated resources.

## Consoles and recording

Docker consoles use an agent-authorized `/bin/sh` exec with TTY. The agent transfers only the established stream FD to the worker, not the Docker socket; resize remains scoped to that exec identity. Explicit close verifies termination of the identity-pinned exec leader even when the recorder unit is already gone. Docker recorder units have an independent systemd `ExecStopPost` cleanup hook, including on worker failure or idle exit. Its short-lived trusted root helper uses the journaled exec/container identity and a pidfd; it kills only that exec leader and confirms Docker reports it stopped. The hook runs outside the recorder filesystem restrictions so it can contact Docker; the recording process still cannot access the Docker socket. Exec creation and cleanup share a file lock. Failed session startup also attempts scoped cleanup. SSH consoles use a host PTY, strict pinned known-hosts verification, a fixed contract user and declared management address. Browser input cannot choose host commands, credentials or QMP operations. Serial sessions live with the VM.

Output records preserve opaque bytes, sequence, monotonic time and output offset. Exact input recording is opt-in at session creation and continuously indicated in the UI; otherwise only input activity is recorded. Output can still contain echoed secrets. Writer access is a single fifteen-second lease. Explicit takeover fences the old token, and expired tokens cannot renew. Reconnect starts as a viewer and replays retained output. PTY resize is recorded and forwarded to SSH or the authorized Docker exec.

`output.partial` has an eight-byte `GLTERM1\0` header followed by little-endian records: type u32, payload length u32, sequence u64, monotonic nanoseconds u64, output byte offset u64, then payload. Types are output (1), resize (2), lifecycle/audit (3), opt-in input (4), and reserved gap (5). Recording pause is not currently exposed. Files sync periodically; finalization syncs and publishes `output.glterm` without replacement. Partial tails remain visible during replay; bytes are never silently repaired. Closed files are downloadable through the run artifact API with SHA-256 verification in the browser, including after destruction.

Each recording has a 64 MiB budget. Session admission checks a 1 GiB filesystem reserve and limits sessions to sixteen per run. SSH/Docker idle timeout is thirty minutes. Recording failure closes the source and leaves incomplete evidence; there is no silent unrecorded continuation. Disk competition by unrelated writers and hard real-time durability are not guaranteed. VM memory admission includes guest RAM plus 512 MiB overhead; ordinary console workers have 128 MiB systemd limits. Workers have read-only filesystems except their session directories, `NoNewPrivileges`, and inaccessible Docker sockets. These trusted root-supervised workers are not a VM security boundary for hostile guests.

## API and browser

`POST /api/v1/runs/{id}/terminal` supports list/open/status/acquire/renew-writer/revoke/input/resize/replay/close. Open uses a declared node; later operations use its registered session ID. Browser identity is derived from the authenticated session, not a submitted owner string. Mutations require the existing CSRF and Origin checks.

`/api/v1/terminal` upgrades only with an authenticated session, allowed Origin and `graphlab.terminal.v1` subprotocol. Each JSON control frame carries runId, sessionId, operation, params and csrf; authentication is checked again for each request. Incoming messages are limited to 4 KiB and 64 messages/second, and queued responses to 1 MiB. Replay uses binary frames with big-endian sequence u64, output offset u64, type u32, length u32, then opaque payload, followed by a JSON cursor response. Input remains bounded base64 JSON; it is not a binary input channel. Browser replay renders through xterm.js without HTML, link or clipboard integration.

## Qualification

See [verification evidence](validation/m4-verification.md). M4 is qualified on the two supplied guest profiles and the shared Docker fixtures. Linux x86, reboot recovery, exhaustive crash windows, general third-party guest readiness, scale and hostile-terminal fuzzing are not established by these tests. Direct QEMU-to-workload data edges remain future work; QEMU-to-OVS connections are supported within arbitrary validated graphs.
